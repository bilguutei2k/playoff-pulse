# AGENTS.md

## Project Identity
- Playoff Pulse has two parts. **The live forecast** (`/`, since November 2026) gives a win probability for every NBA game on the day, plus playoff and title odds, updated automatically and scored against a public sealed ledger. **The 2026 retrospective** ("a traceable NBA playoff forecasting experiment") is a frozen archive of the manually configured 2026 postseason. Rules below name which part they cover where it matters.
- It is deployed at https://548-sable.vercel.app. The homepage (`/`) is the live forecast: today's games, title odds and the track record. `/odds` is the full season forecast and `/how-it-works` explains the live model. The 2026 retrospective narrative lives at `/retrospective`; the frozen completed-season dashboard lives at `/snapshot`; `/evidence`, `/methodology` and `/lab` complete that archive. `/live` and `/live/methodology` permanently redirect to `/` and `/how-it-works`, and `/case-study` to `/retrospective`.
- Live model: `src/lib/season/`, frozen in `src/lib/season/params.ts` as `LIVE_MODEL_VERSION` (`live-2026.27-v2`, v1 plus the injury adjustment). `REFERENCE_MODEL_VERSION` (`live-2026.27-v1`) keeps sealing its own rows so its record continues. Gates, ship rule and every amendment are in `docs/live/registration.md`; results are in `docs/live/evaluation-*.json`. The v2 inputs in `params.ts` are copied from `docs/live/injury-fit.json`; that file and `docs/live/evaluation-injury.json` are frozen and are never regenerated or edited. Changing a parameter requires a new version, and the public record is reported per version. Never refit on all history or tune against validation seasons.
- All public claims are gated by `docs/claims-ledger.md`. Statistical significance for the pooled 360-series backtest lives in `docs/backtest/significance.json` (regenerate with `pnpm exec tsx scripts/backtest/significance.ts`); the immutable pre-2026 record lives in `docs/backtest/frozen-2003-2025/`; parameter provenance is recorded in `docs/parameter-provenance.md`. Do not add performance claims that are not supported by those documents — in particular, the full model does NOT conclusively outperform SRS-only or net-rating-only baselines and must never be framed that way.
- Research promotion is gated by `research.json → modelSelectionGate`: exactly one primary challenger (`exact_srs_logit_plus_seed_v1`), series Brier as the primary endpoint, a 0.005 minimum meaningful improvement, a season-clustered interval below zero, no-worse log loss/calibration, production-equivalent inputs, and a genuinely future archived season. Historical point improvements alone are never sufficient.
- Featured content (replay series, failure examples) is selected by the mechanical rules in the claims ledger, never editorially.
- It is not a betting product. For the 2026 archive, modeling inputs — team ratings, player impact, projected minutes, injury statuses, and model weights — remain manual configuration. The pooled reconstruction covers 645 playoff series and 3,375 pregame states (1984–2026), including era-correct series formats. Rolling-origin evaluation covers 3,160 games and 600 series (1987–2026). The separately scored 2026 holdout covers 85 games and 15 series; both challenger registrations are `CONTAMINATED_2026`. Historical availability coverage is zero and injury effects are not claimed. A 105-series FiveThirtyEight comparison is an external model benchmark, not a market benchmark; timestamped no-vig market coverage remains zero. See docs/backtest/methodology.md and docs/claims-ledger.md. It is not production-grade for unsupervised public use.
- Live data updates automatically through `.github/workflows/live-forecast.yml` + `scripts/live/pipeline.ts`, which commits `data/live/**` to `main`. Data commits never deploy: pages render with incremental static regeneration (`revalidate = 60`, dynamic routes on demand) and read `data/live` at render time from `raw.githubusercontent.com`, through `src/lib/live-data/published.ts` only. Each render resolves `main`'s head commit from git's public ref advertisement and reads every file at that commit (a branch URL is cached by GitHub's CDN for five minutes and ignores query strings), so a data commit shows within about two minutes. A failed or invalid read falls back to the copy bundled at build time. `vercel.json`'s ignore step cancels the build of every commit that changes only `data/live/`; code commits deploy as before. Vercel still counts those canceled deployments toward Hobby's 100 a day, so on busy days a code or preview deploy can be rate-limited, while the site keeps updating because it does not depend on deploys. Publication fails closed: any validation failure publishes nothing and fails the job. There is no PR gate on this path, because a human gate cannot keep up with a daily slate. Humans do not edit `data/live/**`.
- `data/live/` layout: `state.json` (the published state, schema 2), `ledger/{season}.jsonl` (append-only), `games/{year}.json`, `boxscores/{year}.json` (compact box scores for the live season, `StoredBoxScores`), `reports/{season}/{etDate}.json` (every NBA injury report the job downloaded for that slate, keyed by its header timestamp, cut to the slate's games), `injuries/{season}/{etDate}.json` (ESPN's injury list with its return dates, stored for study only), `snapshots/`, `health.json`, `heartbeat.json`, and `site/`: compact copies of the ledger for the site, rewritten from the ledger on every run (`site/{season}/days/{etDate}.json` with every seal row of that ET date, `site/{season}/months/{yyyy-mm}.json` with every row of that month's games minus seals' `drivers`, and `site/manifest.json` with the SHA-256 of each file the site reads, which it uses as cache keys). The full ledger outgrows the 2 MB data-cache item limit during the season, so the site never fetches it once a manifest exists.
- `src/lib/data/playoff-config.ts` is the frozen 2026 archive, with no automated updates. `scripts/refresh-data.ts` remains only as history; its workflow has been removed.
- Finalized results enter the live model only through the validated pipeline. Live, in-progress scores reach only the in-game estimator (`src/lib/season/in-game.ts`) and never change ratings or a sealed forecast. The NBA injury report is a v2 model input, only through the validated pipeline: statuses on the report in use at a seal give each team's expected absence, and current absences carry into the season simulation for their survival-table length. ESPN's injury list (including its `returnDate` and `fantasyStatus`) and market odds are captured for study and displayed as described in `/how-it-works`; they are never model inputs.

## Hard Model-Correctness Rules
- Probabilities MUST be bounded between 0 and 1. Validate at output boundaries.
- Series simulation MUST respect the current series score: from config in the 2026 archive, from observed games in the live model.
- Home-court pattern MUST apply to the correct remaining games, not arbitrary games.
- In the 2026 archive, injured or out players MUST affect projected minutes or impact; out means 0 contribution. The live model (v2) models injuries only through the NBA injury report: listed players' expected absence weighted by status, and return estimates from the frozen survival table. The UI MUST say what is modeled and what is not (unknown future injuries, minutes redistribution, matchups), and MUST label any number from a model without the injury term.
- Stronger teams MUST win more often in simulation. This is a verifier invariant.
- Equal teams on neutral court MUST be near 50/50.
- Random number generation MUST be seeded; same inputs must produce same outputs.
- Historical backtests MUST NOT use future data. Check available-at-time-of-prediction.
- Historical rotations and external benchmarks MUST fail closed when timestamped pre-deadline coverage is absent. Never infer a rotation from later participation or invent an external probability.
- UI probabilities MUST NOT use fake precision. One decimal point is enough.
- New probability outputs MUST add or reuse invariants in `scripts/verify/invariants.ts` (generic), `scripts/verify/data-snapshot.ts` (2026 archive assertions), or `scripts/verify/live-checks.ts` (live path).

## Live Forecast Rules
- The forecast ledger (`data/live/ledger/*.jsonl`) is append-only. Committed rows are never edited or removed. `pnpm verify:ledger` enforces this.
- A sealed forecast uses only results from before its ET date. Never backfill a seal. A game that tips unsealed is recorded as missed and counted publicly.
- v2 seals each game twice from the same previous-ET-date ratings: a morning seal, and a final seal by the first run with `0 < tip - now <= 60 minutes` using the latest validated report at or before now. The final seal is scored; a game without one is scored on its morning seal and counted as "no final seal", never as missed. v1 keeps its single morning seal. Seals, misses and records key on (game, model version, seal kind). Report fetch, parse and validation happen before sealing; a failed report uses the last good one under 24 hours old and flags the row, otherwise absences are zero and the row says availability was missing. A report is usable when at least half of the slate's games appear on it; a team or game not on it has nobody listed. A team the report in use marks NOT YET SUBMITTED is not a team with nobody listed: on morning, reissued and final seals alike, its side takes the team's expected absence for that game from current absences, the charge the season simulation makes for its next game, and the row records `unfiled: { home, away }`. Every v2 seal stores all players with positive points on each side as `drivers`, largest first, with `driversComplete: true`; they add up to `absencePoints` within 0.01 and never feed the number. Rows written before that rule (2026-11-03 amendment) kept at most three drivers and counted nobody for an unfiled team; the UI rebuilds their lists from the stored report without inventing per-player points. A morning seal with availability missing is reissued once (`sealKind: "reissued"`) by the first run with a usable report more than an hour before tip, under its true issue time; the original row stays, and scoring takes final, else reissued, else morning. Report problems set `reportProblem` in `health.json`, and the job opens one issue per slate; they never fail the job.
- Slates and all date logic use `America/New_York`, never the UTC date. The engine keys on ESPN numeric team IDs; repo team codes go through the fail-closed map in `src/lib/season/teams.ts`.
- Provisional forecasts exist only so every game has a number when the job runs late. They MUST be labeled, and MUST NEVER enter the ledger or the record.
- Performance claims follow the live section of `docs/claims-ledger.md`. Results are labeled small-sample below 500 scored games, and missed and incomplete seals are always shown.
- Season, tiebreak and format rules live in `src/lib/season/formats.ts` and `standings.ts`. A new season fails closed until it is registered in `formats.ts`.
- Team logos are 56px copies of ESPN's default logos, downloaded 2026-11-01, in `public/logos/nba/{espnTeamId}.png`. They are NBA and team trademarks, used without a license by the owner's decision. Show them only through `src/components/live/TeamLogo.tsx`, small and unaltered, always beside the team's name or abbreviation. `SHOW_TEAM_LOGOS` there turns them all off. Keep the "not affiliated" notice on `/` (the site footer carries it on every page).

## Never Do
- Never put forecasting math in UI components.
- Never import from `src/lib/live-data/` inside `src/lib/model/` or `src/lib/season/`. The dependency runs one way: the adapter may use engine types, never the reverse.
- Never pass live, unfinished scores into anything except the in-game estimator.
- Never claim official NBA data sources. The live path uses ESPN's unofficial public feeds and the NBA's public injury report PDFs (`ak-static.cms.nba.com/referee/injury/`), which are unofficial for our purposes: Playoff Pulse is not affiliated with the NBA and reads them without any arrangement. The report host refuses bursts, so fetch one file at a time with pauses. The live path's authoritative timestamp is `generatedAt` in `data/live/state.json`; each report's own header timestamp, never its file name, decides when it was known. The 2026 archive is manually configured, and its snapshot time is `dataLastUpdatedTimestamp` in `src/lib/data/playoff-config.ts`.
- Never hide placeholder or manual-data caveats. Keep caveats visible in the UI.
- Never make betting recommendations or use betting framing. Market odds are displayed per game as a reference, comparison only.
- Never present model output as authoritative beyond what has been validated.
- Never hard-code team IDs inside model functions. Look teams up through config or typed maps.
- Never use unbounded probability operations that could produce values outside [0, 1].
- Never write simulations that do not terminate correctly; every series ends at 4 wins.
- Never produce randomness that changes on re-render. Keep stochastic work out of render paths.
- Never broadly rewrite working code without a stated reason and user approval.

## Architectural Layers
- Data/config layer: `src/lib/data/` owns manual teams, players, ratings, injuries, projected minutes, series state, home patterns, and model settings. Do not put forecasting math here.
- Live-data adapter: `src/lib/live-data/` fetches and strictly validates ESPN payloads and the job's published files. `published.ts` is the only reader of `data/live` in the site (scripts keep reading the filesystem). `espn-season.ts` feeds the pipeline and `/api/live/today`. `/api/live-scoreboard` remains the 2026 dashboard's display probe.
- Season engine: `src/lib/season/` holds pure functions for ratings, game forecasts, the in-game estimate, standings, season simulation, sealing rules and the slate view. No React, no fetch, no file access.
- Pipeline: `scripts/live/` runs ingestion, fitting, evaluation and the scheduled job. Only `pipeline.ts` writes `data/live/**`.
- Model engine layer: `src/lib/model/` contains pure reusable TypeScript functions for player-minute impact, team strength, expected margin, win probability, series simulation, and bracket Monte Carlo.
- Model modules MUST NOT import React or UI code.
- UI layer: `src/components/` and `src/app/` display model outputs and controls. They MUST NOT contain Monte Carlo logic, probability formulas, or rating math.
- Methodology layer: `src/app/methodology/page.tsx` covers the 2026 archive; `src/app/how-it-works/page.tsx` covers the live forecast. Both state assumptions and limitations.
- Evaluation layer: `scripts/` contains verification now and may contain backtesting or calibration later.

## Workflow Rules
- For non-trivial changes, propose a plan first and wait for approval before writing code.
- When uncertain about a modeling decision, state the uncertainty and propose options. Do not silently pick.
- New model components need types, a pure function, a verify-script invariant, and a methodology update or TODO.
- Keep TypeScript strict. Do not loosen types to silence errors.
- Use existing dependencies and patterns unless the user approves a package or architecture change.
- Before claiming done, run `corepack pnpm verify` and `corepack pnpm build`.
- Use `corepack pnpm lint` when touching lint-sensitive app code; note existing lint scope if unrelated files fail.
- Use `corepack pnpm dev` for local development and `corepack pnpm start` for production start checks.

When claiming a task is done, include the actual output or summary of the verify/build commands you ran. Never claim a check passed without running it in this session.

## Verification Expectations
- `corepack pnpm verify` runs `scripts/verify-model.ts`, which runs both halves of the verifier:
  - `scripts/verify/invariants.ts` (`pnpm verify:invariants`) — generic model invariants that must hold for any valid config: equal teams near 50/50, stronger teams/home court/adjustments/injuries move probabilities the right way, series terminate at 4 wins and respect the home pattern, a 3-0 lead massively improves series probability, title probabilities sum to ~100%, no reach probability exceeds 1.0, and live scoreboard normalization (display-only) maps games, scores, and ESPN abbreviation aliases.
  - `scripts/verify/data-snapshot.ts` (`pnpm verify:data`) — assertions describing the frozen 2026 snapshot (rosters, series scores, bracket state).
  - `scripts/verify/live-checks.ts` (`pnpm verify:live`) — published state (schema 2, records for both versions, frozen injury tables), forecast sums, the injury invariants (more absence lowers a team's chance, replacement-level absence changes nothing, equal teams with equal absences stay even, absences never negative, status table monotone, long bucket-0 at least short), seeding against five real seasons, ledger validity, and that `data/live/site/` is exactly what the ledger, state and games produce (skipped until the job first writes it).
- `pnpm verify:ledger [baseRef]` checks that the ledger only grew. CI runs it against `origin/main`.
- The live-forecast workflow runs `verify:ledger` and `verify:live` before every commit. Its pushes use `GITHUB_TOKEN`, so they do not trigger `ci.yml`. Its report alert is `scripts/live/report-alert.sh`; `.github/workflows/report-alert-test.yml` (run by hand only) exercises it with a fake problem.
- New model features should add focused invariants before UI polish.
